# What-I-Want

----







## 🚀 트러블 슈팅: 대용량 데이터(100만 건) 조회 성능 최적화 및 OOM 해결

### 🚨 Issue (문제 발생)
실무와 유사한 환경을 구축하기 위해 더미 데이터 100만 건을 적재한 후, 버킷리스트 목록 조회 API와 키워드 검색 API를 테스트하는 과정에서 치명적인 성능 저하 및 서버 다운 현상이 발생했습니다.
- **전체 조회 API:** 서버 메모리 초과로 인한 `OutOfMemoryError(OOM)` 발생 및 API 호출 실패.
- **검색 조회 API:** `content` 필드에 특정 키워드("말아톤")가 포함된 33,334건의 데이터를 조회할 때 **11.5초(11,522ms / 처음 실행 기준)**의 타임아웃급 지연 발생.

### 🔍 Cause (원인 분석)
1. **메모리 초과 (OOM):** 100만 건의 데이터를 DB에서 한 번에 가져와 스프링 부트의 JVM 메모리(Heap)에 모두 엔티티(Entity) 객체로 올리려다 메모리 용량(1GB 서버 한계)을 초과했습니다.
2. **네트워크 및 직렬화 병목:** 검색된 3만여 건의 데이터를 네트워크를 통해 WAS로 끌고 와서, 거대한 JSON 객체로 직렬화(Serialization)하는 과정에서 극심한 병목이 발생했습니다.
3. **Over-fetching:** 사용자는 한 화면에서 모든 데이터를 볼 수 없음에도, 불필요하게 많은 데이터를 조회하여 DB I/O와 서버 자원을 낭비하고 있었습니다.

### 💡 Solution (해결 방안)
클라이언트가 한 번에 볼 수 있는 데이터만큼만 나누어 제공하도록 **페이지네이션(Pagination)**을 적용했습니다.
- DB 조회 시 `LIMIT`과 `OFFSET`을 사용하여 한 번에 필요한 개수(예: 20개)의 데이터만 WAS로 페치(Fetch)하도록 쿼리를 최적화했습니다.
- 응답 데이터의 크기를 대폭 줄여 JSON 직렬화 및 네트워크 전송 시간을 최소화했습니다.

### 📊 Result (개선 결과)
페이지네이션 적용 후, OOM 에러를 완벽히 해결하고 **검색 API 응답 속도를 약 91.4% 단축**시켰습니다.

| API 종류 | 개선 전 (Before)                 | 개선 후 (After)                 | 개선율 |
| :--- |:------------------------------|:-----------------------------| :--- |
| **전체 목록 조회** | `OutOfMemoryError` (실패)       | **1.85s (1,850ms)**          | 정상화 및 안정성 확보 |
| **키워드 검색 조회** | `11.5s (11,522ms / 처음 실행 기준)` | **0.99s (996ms / 처음 실행 기준)** | ⏱️ **약 91.4% 속도 향상** |
*(※ 테스트 환경: AWS EC2 t2.micro, Postman 호출 기준)*

### 🎯 Next Step (V2 고도화 계획)
페이지네이션을 통해 WAS의 메모리 부담과 네트워크 병목은 해결했지만, 검색 API에서 여전히 약 1초의 지연이 발생하고 있습니다. 이는 DB 단에서 `LIKE '%키워드%'` 조건으로 인한 **Full Table Scan**이 발생하기 때문입니다.
향후 V2 업데이트에서는 다음 기술을 도입하여 응답 속도를 **0.1초(100ms) 이내로 최적화**할 계획입니다.
1. **커서 기반 페이징 (No-Offset):** `OFFSET` 스킵 오버헤드 제거
2. **Full-Text Search (전문 검색):** 인덱스를 활용한 텍스트 검색 속도 극대화
